## Pirates of the Agentic Workflows

I want to focus in this article on some of the problems with AI agents, which I think are very common and require some discussion. All of us have our unique way of managing our agentic workflows, however several issues pop more than often when working and collaborating on larger projects.

* **Long-lasting Memory** - how to make the agent know what I'm working on and what are the principles behind it, without reading my entire codebase every time I start a new session
* **Context Management** - the agent is forgetting very specific instructions that I gave it not long ago, because the context was compressed and specifics are lost OR my context is so complex that the agent requires a lot of steering to implement details correctly
* **Organisation of Work** - the organisation of long-term documentation and short-term specifications is critical for efficient agentic workflows, especially on bigger projects with continuously growing complexity
* **Optimization of Cost** - them new models (like Anthropic's Fable 5, at the time of writing this) can cost significantly in very short periods of time, if not used wisely

## Fighting windmill giants

Every time when you start a new chat (session), the agent has access to some memory, instructions, skills and so on. Whatever you have it, it's there, but until you send a prompt, it hasn't read any of it. Each session starts as empty as my soul. Vendors have memory mechanisms, but how they work is out of reach for us. Even if something is disclosed, it doesn't paint the whole picture.

Each agent has different behavioural configuration, guardrails, input filters (shoutout to all my homeboys running their homegrown AI setup), training data and a multitude of various other variables, which makes it incredibly hard to assume how or why it acts the way it does, but what we know for sure is that the first thing the agent will read right after your first prompt is `CLAUDE.md`/`AGENTS.md` - the [main system prompt file](/blog/2026/01/claude-code-system-prompting-and-commands/#configuring-claudemd). After that, it's a matter of configuration and reasoning what's being read next, unless you started a `/slash-command` which targets a specific skill. 

<Highlight block color="pink">
  > #### Context Bloating
  >
  > This is the first time you've polluted and bloated your context. Assuming that you have crafted your system prompt successfully, still, a large portion of the jobs that you task your agent with will use only a portion of that information to be completed. Either way, that's memory used within a limited memory space.
  >
  > The same thing happens for every custom `/command` that is used only once, but doesn't complete the whole job. Every assumption and test, failed research that lead to more research. All this stays in the context of the current conversation (session) and as it grows, confusion and hallucinations increase, as the bot strives to satisfy. Inevitably 

</Highlight>

Context is constantly polluted by information that isn't directly relevant to the execution of your task. Bloated contexts produce messy execution and usually lead to steering the model with additional prompts. The less specific the prompts, requires of the agent to do more research to decide how to implement the solution.

## Improved Agentic Memory

There're multiple aspects and approaches to improving one's agent's memory, some focus on what tasks have been completed or what architecture and patterns exist, other focuses on the reasons behind the action - why things are built the way they are.

Some people argue one is more important than the other, I argue that arguing about it is a waste of time - one should have both effect and causality and that's a fact of life!

### Mem Palace

When it comes to pure memory organisation, there's one project that stands out the most, that was released not long ago by the star of [The Fifth Element](https://www.imdb.com/title/tt0119116/), [Milla Jovovich](https://github.com/milla-jovovich).

<GithubLink url="https://github.com/mempalace/mempalace">
  > **Mem Palace** stores your conversations in a searchable form, in order to keep reasoning behind decisions in the loop. It **works as a local MCP service**, which can scan/learn from existing codebase and will auto-learn as you use it.
  >
  > `Fun Fact:` the data model is inspired by Roman and Greek "Memory Palace" concept and projects, topics and so on are organised in wings, rooms and drawers.
</GithubLink>

It's a plug and play searchable memory building block, one of many.

### Managing commits

I used to forbid my agents from committing for me, but then I added better instructions to keep my commit messages `terse` and focused on **features added or modified** with **minimal reasoning behind the change**.

My `git log` became a clean and meaningful source of truth about what's been done in the project, change by change. In combination with `beads`, my commit messages became even more granular and meaningful, without being too explicit. Now I can use this in my `CLAUDE.md`/`AGENTS.md` and skills and lead the agent to read the log, when debugging an issue, for example.

### Small cap models

I require less steering, when working with smaller context to plan and then again small context to execute. Where large context models really shine is when you start doing **overnight runs**.

### RECIPE: "Disco at the Large Cap"

Here's how one would do overnight runs, for various reasons like, planning work for a project, while the agent is working on something, maybe an entire different project. Planning before execution helps the agent to build a "big picture" context before executing tasks. Here's the recipe:

<Highlight block color="green">
> 1. You plan a bunch of stuff that you want to happen during the day
> 2. You start a large context session and tell your agent to execute all outstanding tasks without asking for permissions, by following the planning for all outstanding tasks (best manageable with a tool for task organisation like `beads`)
> 3. Go to bed
</Highlight>

A bit risky, **can be done**! Just [use devcontainers to protect your environment](/blog/2025/claude-code-devcontainers/), something I'm doing less and less nowadays and I'm relying on Claude and Cursor's built-in Bash sandbox using Apple's Seatbelt and abusive command filtering, but mostly praying.

## On-demand context

There're 2 common ways to battle context/state growth and pollution:

  1. Break the work in two stages - use the <ClaudeCommand name="plan" external /> mode, instead of telling the agent directly what to do. Let it create a work plan and act on it. This is where your ***smarter, more expensive models*** come to play.
  2. Keep work in small chunks, preferably start a new clean session before execution that focuses on executing instructions, rather than doing research.

### SDD with OpenSpec

This is where [spec-driven development (SDD)](https://mifkata.com/blog/2026/01/claude-code-spec-driven-development/)
really shines and couple of tools need to be mentioned.

<GithubLink url="https://github.com/Fission-AI/openspec">
> Probably the easiest to grasp, most plug-n-play solution to leverage your <ClaudeCommand name="plan" external /> game. Using it will leave you with documentation in a few stages and level of detail: `proposal` - a rough overview of the work that's to be done, `design` - a more profound explanation of changes with deeper technical detail, `tasks` - an extensive list of steps for the agent to follow and verify complete during execution and `specs` - the final feature definition, which is persisted after the `openspec` has been applied and archived.

</GithubLink>

Using **OpenSpec** allows you to split the work in 2 sequential agent sessions - planning and execution (aka the gateway to **overnight runs**), while preparing your plan in multiple steps, allowing you to review and detect discrepancies early during the planning stage.
